# vendor-vetting

**Agentic document vetting for supplier onboarding, built against the Dominican
Republic's public procurement registry requirements.**

> ⚠️ **Independent portfolio project. No affiliation** with the Dirección General de
> Contrataciones Públicas (DGCP), the DGII, the TSS, or any institution of the
> Dominican state. **Every document in this repository is synthetic** — generated by
> the code in `src/synth`, depicting no real person or company. Nothing here should be
> used to make a real procurement decision.

---

## The problem

To register as a state supplier in the Dominican Republic (the *Registro de Proveedores
del Estado*), a company submits a folder of certifications: proof it legally exists,
proof it is current on its taxes, proof it is current on social security, and the ID of
whoever signs on its behalf. Today a person opens each file, reads the dates, checks the
identifiers, and compares the company name across all four to make sure they describe the
same company. It is careful, repetitive work, and the failure mode that matters is not
rejecting a good packet — it is *accepting a bad one*, because nobody looks again.

This system takes an unlabeled folder, works out what each file is, extracts the fields,
validates them, cross-checks the documents against each other, and produces a dossier with
a `pass` / `warn` / `fail` / `needs_review` status per requirement, each linked to the exact
page and region that supports it.

## The one principle

**The model extracts. The code validates.**

The LLM's only job is to read a document and report what it says, with a confidence score
and a page citation. It is never asked to judge, decide, or reason about a business rule.

| | |
|---|---|
| ✅ Asked of the model | *"What issue date appears on this document?"* |
| ❌ Never asked of the model | *"Is this document expired?"* |

Expiry, check digits, status thresholds and cross-document consistency are deterministic
code with unit tests. A date arithmetic bug is findable and fixable; a model that decided
"expired" for reasons it cannot show you is neither.

This is enforced, not merely intended: `src/models/prompts.test.ts` fails the build if the
words *vencido, vigente, válido, aprobar, rechazar, cumple* — or a day-count window, or
any cross-document comparison — appear in a prompt. It has caught me once already, on a
prompt where I had written "un acuerdo de pago **vigente**".

## Architecture

```
  folder of unlabeled files
            │
   ┌────────▼────────┐
   │ ingest          │  magic bytes, not filenames; SHA-256; duplicate detection
   ├─────────────────┤
   │ render          │  PDFs → text layer + per-fragment geometry
   │                 │  images stay images (no deskew, no denoise — see Failure modes)
   ├─────────────────┤
   │ classify        │  ← model     one of 4 types, or `unknown`
   ├─────────────────┤
   │ extract         │  ← model     per-type schema, structured output
   ├─────────────────┤        { value, confidence, page }
   │ normalize       │  dates parsed, identifiers stripped — deterministic
   ├─────────────────┤
   │ locate          │  find each value in the text layer → bbox
   ├─────────────────┤
   │ validate        │  ▲ no model past this line ▲
   │ cross-check     │  check digits · date sanity · freshness · status
   ├─────────────────┤  RNC, razón social and representante agree across documents
   │ dossier         │  pass · warn · fail · needs_review, with evidence links
   └─────────────────┘
```

Every stage writes to `stage_runs` with its duration, tokens and output, so a stage can be
re-run without repeating the model calls before it — and so the latency and cost tables
below are measured rather than estimated.

### Confidence is a third answer, not a threshold

A field extracted below `CONFIDENCE_THRESHOLD` (0.75) is **not** rejected. It goes to a
review queue, and the requirement that depends on it reports `needs_review` — which
outranks even `fail`.

The reasoning: an extraction the system does not trust cannot prove a document is bad any
more than it can prove it is good. Auto-rejecting on low confidence would convert "I
couldn't read this" into "this supplier is non-compliant", which is a worse error than
asking a human to glance at it.

## The four documents

| Document | Input | The technical problem it forces |
|---|---|---|
| Certificación de Registro Mercantil | text PDF | structured extraction; **explicit** printed expiry |
| Certificación de cumplimiento fiscal (DGII) | text PDF | a **status enum** classified from varying prose; **implicit** expiry |
| Certificación de la TSS | text PDF | third carrier of `rnc` + `razon_social` — makes coherence meaningful |
| Cédula del representante legal | **scanned image** | different modality; name must match the Registro Mercantil |

## Results

`qwen2.5:7b` (text) + `qwen2.5vl:7b` (vision), both **Q4_K_M**, via Ollama on a local
RTX 4070 Laptop (8 GB). 40 synthetic dossiers, 160 documents. Full report:
[`eval-results/2026-08-19-0251-qwen2.5-7b.md`](eval-results/2026-08-19-0251-qwen2.5-7b.md).

### False passes — the metric that matters

A defective dossier reported clean tells a reviewer there is nothing to look at. It is
reported on its own and never averaged into anything.

> **0 of 16 defective dossiers were reported as `pass`.**

### Verdicts — 100.0% (40/40)

|---|---:|---:|---:|
| **pass** | 14 | 0 | 0 |

### Classification — 100.0% (160/160)

Including **40/40 degraded cédula scans** — rotated 1–5°, gaussian noise, JPEG artifacts,
uneven lighting, partial crops.

### Extraction — 100% precision and recall on all 19 fields

Precision is *when the model answered, was it right*; recall is *of the fields present,
how many did it get*. An abstention counts as a miss, never as a wrong answer.

## How to read these numbers

**A 100% on a corpus I generated myself is not evidence the system reads real documents.**
It is evidence of something narrower and still worth having: that the pipeline is correct
end to end, and that when a verdict is wrong the fault is unambiguously in extraction
rather than in the rules.

The corpus is clean typography, my own vocabulary, and degradations I wrote. Real intake
brings scanner artifacts I did not think of, phrasings I did not anticipate, and layouts
that change without notice. Expect these numbers to fall on real documents. The eval
harness exists so that when they do, the drop is measured instead of discovered by a
supplier.

**I predicted the degraded cédula would be where a 7B quantised vision model lost the most
ground. I was wrong** — it classified 40/40 and extracted all four fields without an error.

## Failure modes

### Self-reported confidence carried no information at all

Across the full corpus — **761 extracted fields — every single one came back at
confidence exactly 1.00.** Minimum 1.00, maximum 1.00, zero variance.

And the one extraction error the pipeline ever made also came back at 1.00.

So the confidence threshold, the review queue, and the `needs_review` status are all
built, tested, and wired end to end — and on this model and this corpus the signal that
drives them is a constant. The review queue renders "nothing pending" not because the
extractions were verified, but because the model never once expressed a doubt.

This is the project's most uncomfortable result and the one worth publishing. Asking a
model how sure it is returns a number shaped like evidence, and here it was decoration.
The honest alternative — aggregating per-token logprobs per field — is not usefully
exposed by the Ollama chat API.

Two things follow, and the design already assumes both. Low confidence routes to human
review rather than to automatic rejection, so a miscalibrated number cannot reject a
valid supplier. And **no requirement is ever decided by confidence alone**: every verdict
comes from deterministic rules over the extracted values, which is why the dossier
verdicts are still 40/40 despite the confidence signal being useless.

A hosted model with real logprobs would be the first thing to measure against this.

### Column gutters were being collapsed, and the model got blamed

An extraction returned `"Empleador Servicios Punta Alta, E.I.R.L."` — the field label
glued to the value, which then failed the cross-document name check. It looked like a
model failure. It was mine: `fragmentsToText` joined every fragment on a line with a single
space, so a ~100pt column gutter and a word space became the same character.

Fixed by emitting a tab when the horizontal gap exceeds 2% of page width. **This was the
only extraction error in the corpus**, and it was a bug in my own text reconstruction.
Worth stating plainly: the first instinct was to reach for the prompt.

### The synthetic watermark broke classification

Cédulas classified as `unknown` at first. Asked to explain, the model said:
*"El documento parece ser un ejemplar sintético de identidad, ya que menciona «EJEMPLAR
SINTETICO - SIN VALIDEZ LEGAL»"*. The watermark this project requires for honesty was
causing the model to reject the document as not-a-document.

Fixed with an instruction that such markings do not determine document type. Worth noting
as a general hazard: **safety markings on synthetic eval data can become the thing the
model keys on.**

### Both models do not fit in 8 GB, and everything downstream of that

`qwen2.5` (~4.7 GB) and `qwen2.5vl` (~5.4 GB) together exceed the development GPU, so
something has to be swapped. Three separate failures came out of that one fact.

**Alternating per dossier exhausted VRAM.** `CUDA error: device not ready` mid-run, while
`/api/ps` still reported the model resident and `nvidia-smi` disagreed. Fixed in the eval
by grouping work by model — all text documents, unload, all images — which is both more
reliable and faster. On a backend with room for both, `unload` is a no-op and the ordering
costs nothing.

**The swap thrashed the host, not just the GPU.** Processing folder by folder, as real
intake would, means two ~5 GB model loads per dossier through a 9.7 GB WSL host. The OS
killed the loader twice. Grouping by model is the answer at batch scale; a single dossier
arriving on its own pays the swap once and does not care.

**Losing the GPU entirely was silent.** Restarting Docker Desktop broke WSL's GPU
passthrough, and Ollama did not error — it fell back to CPU and kept answering. Text extraction merely got slow; the 7B vision model stopped
finishing inside the 180-second timeout, so **every scanned cédula failed**, `completeness`
failed with it, and seven dossiers were written as `fail` for a reason that exists nowhere
in the documents.

Read from the top, the evidence pointed at the model: timeouts, in the extract stage, only
on the vision path. The tell was elsewhere — `/api/ps` reporting the model resident with
`size_vram: 0`.

Two lessons, both cheap. A backend that degrades instead of failing will hand you a
plausible wrong story about your own code. And the fix for the re-run was not a code
change but a check before it: warm the vision model and assert it landed in VRAM, rather
than discovering an hour later that it hadn't.

### Check digits have a known false-negative rate on real data

`python-stdnum` ships whitelists of ~23 RNCs and ~1,500 cédulas that are genuinely issued
but fail their own checksums. **Those whitelists are deliberately not vendored here** —
they are real taxpayer and national ID numbers, and this project handles no real registry
data.

Consequence: against real-world input these validators have a small false-negative rate.
For a vetting system that is the safe direction — a valid identifier gets flagged for
review rather than a bad one passing — but it is a real limitation, not a rounded-off one.

### No image preprocessing, on purpose

`renderImage` does not deskew, denoise or contrast-stretch. Each would be plausible, and
each would quietly become an untested preprocessing pipeline whose contribution to the
final numbers nobody could separate. Start honest; add preprocessing when the eval shows it
earns its place.

### The deployed demo had no filesystem to read from

Documents were referenced by absolute path, which is correct while everything runs on one
machine and useless the moment it does not. Deployed, the dossier would have rendered and
every evidence link would have 410'd — the one part of the UI that carries the whole idea.

Bytes now live in `documents.content` as `bytea`, with the filesystem kept as a fallback for
local development. The corpus is 5 MB total, so this removed object storage and its credentials
from the deployment rather than adding a service to carry synthetic data.

### Scanned documents get no evidence region

The locator searches a PDF's text layer, so a scanned cédula's fields carry no bounding
box, and the viewer says so rather than drawing a plausible rectangle. Recovering it needs
per-word OCR geometry the current vision path does not produce.

Within PDFs the coverage is total: **522 of 522 literal fields located, 100%**. The only
PDF fields without a region are the 79 `estado` values — an enum classified from prose,
so there is no printed string to point at, and inventing a box for it would be worse than
admitting there isn't one.

Asking the model for a bounding box was considered and rejected: it would return a
confident rectangle whether or not the value is there, and a citation you cannot trust is
worse than no citation.

### The eval harness destroyed its own baseline

Result files were named `YYYY-MM-DD-<model>`. Two runs of the same model on the same day
collided, and the post-fix run silently overwrote the pre-fix one — destroying exactly the
before/after pair that makes a fix worth writing up. The pre-fix numbers quoted above were
observed during the session but their results file no longer exists; only the post-fix run
is in `eval-results/`.

Filenames now carry the minute. Reconstructing the lost file by hand was considered and
rejected: a hand-typed file presented as generated output is a fabricated result, which is
the one thing an eval harness must never contain.

### Bugs the corpus found that a demo would not have

- **Deterministic generation, three times over.** The reproducibility test caught sharp's
  unseedable libvips noise, render randomness keyed to array position, and `pdf-lib`
  stamping the wall clock into every PDF's `CreationDate` — which meant *no* generated PDF
  was byte-reproducible.
- **A crash on abstention.** Validation rules ran before the confidence guard, because
  arguments evaluate before the call. A single unreadable field crashed an entire dossier.
  Fixed by making rule evaluation lazy. Ollama never surfaced it: `qwen2.5` abstained zero
  times in 800 fields.
- **The duplicate-document defect broke persistence.** Documents were keyed by content
  hash, so the corpus's two byte-identical files collapsed into one row and their fields
  collided on a unique index. Every dossier carrying that defect failed to store. Found
  only because the corpus injects duplicates deliberately — a demo folder with four
  distinct files would never have surfaced it.

## Running it

```bash
pnpm install

pnpm synth                             # 40 dossiers + ground truth → data/synthetic
pnpm test                              # 296 tests (15 skip without Postgres)

pnpm db:up && pnpm db:migrate          # Postgres 16 in Docker, host port 5433
pnpm ingest --corpus data/synthetic    # run the pipeline, persist results
pnpm dev                               # dossier UI at localhost:3000

pnpm eval                              # score the pipeline against ground truth
```

Needs [Ollama](https://ollama.com) with `qwen2.5:7b` and `qwen2.5vl:7b` pulled. **No API
key, for anything** — the full eval reproduces without an account.

The corpus is gitignored rather than committed: it is a pure function of its seed, so
`pnpm synth` reproduces it byte for byte, and a test asserts that.

Database tests skip rather than fail when no Postgres is reachable, so `pnpm test` works on
a fresh checkout without Docker.

## Deploying it

The app is stateless: all model work happens at ingest time, and the UI only reads Postgres.
So a deployment is the Next app plus a managed database — no Ollama in production, no object
storage, no background workers.

```bash
# 1. point at the hosted database and create the schema
DATABASE_URL='postgres://…' DATABASE_CA_CERT=/path/to/root.crt pnpm db:migrate

# 2. load the corpus from this machine — inference runs locally, only the writes go remote
DATABASE_URL='postgres://…' DATABASE_CA_CERT=/path/to/root.crt pnpm ingest --corpus data/synthetic
```

Loading it this way avoids a dump-and-restore step: the same command that populates a local
database populates a remote one, so what is deployed went through the identical pipeline. The
run against a hosted Postgres reproduced the local numbers exactly — 40 dossiers, 160 documents,
761 fields, the same 40/40 verdicts, and all 160 stored documents SHA-256 identical to the files
on disk.

Roughly 5 MB of document bytes end up in Postgres, which fits any managed free tier.

### TLS is not optional and not `rejectUnauthorized: false`

Managed providers often sign their database certificates with a private root — Supabase uses
"Supabase Root 2021 CA" — which is not in Node's trust store. `ssl: true` therefore fails with
*self-signed certificate in certificate chain*, and the fix the internet reaches for first is
`rejectUnauthorized: false`. That is not a smaller version of TLS; it is TLS with the part that
stops an impostor removed.

So `src/db/ssl.ts` decides this once, and **fails closed**:

| Situation | Result |
|---|---|
| local host (`localhost`, `127.0.0.1`, `::1`, `0.0.0.0`) | no TLS — so `pnpm test` needs no certificates |
| remote **with** a CA certificate | verify |
| remote **without** one | verify, and fail loudly — never a silent downgrade |
| `DATABASE_SSL_INSECURE=1` | skip verification, deliberately greppable |

`DATABASE_CA_CERT` takes either the PEM contents or a path, because a serverless platform's
environment variables are text and not a filesystem. `drizzle.config.ts` imports the same
function rather than restating it: migrations and queries must not disagree about who they trust.

The certificate has to come from the provider's dashboard — for Supabase, **Settings → Database →
SSL Configuration**, not the Connect dialog. It cannot be lifted out of the chain the server
presents, because a root certificate offered by the server you are trying to verify proves
nothing. Verified the downloaded root actually validates the chain before trusting it:

```bash
openssl s_client -starttls postgres -connect <host>:5432 \
  -CAfile root.crt -verify_return_error   # → Verify return code: 0 (ok)
```

### Notes from deploying this one to Vercel + Supabase

Specific to those two, recorded because each cost time:

- **Supabase's direct database host is IPv6-only.** From a network without IPv6 routing it is
  `ENETUNREACH`, with nothing to configure. Both poolers are dual-stack, so use a pooler: the
  **session** pooler (port 5432) for the one-off migrate and corpus load from a laptop, the
  **transaction** pooler (port 6543) for the serverless app, which opens a connection per
  invocation. Parameterised queries work fine through transaction mode on `pg`.
- **A paused or still-restoring Supabase project reports `tenant or user not found`** from the
  pooler — the same message a wrong password would produce, which sends you looking in the wrong
  place. The credentials are fine. The quick way to tell the two apart is DNS: when the project
  is paused, `<ref>.supabase.co` stops resolving altogether, while the pooler host keeps
  resolving and accepting TCP because it is shared infrastructure. If the subdomain does not
  resolve, nothing about the connection string is the problem.
- **Vercel supports pnpm 6–10, not 11**, and only reads `packageManager` when Corepack is
  enabled. With `lockfileVersion: 9.0` it picks pnpm 9 or 10 on its own, which installs this
  lockfile cleanly, so leave Corepack off and leave the local pnpm 11 pin alone.
- Env vars for the deployment: `DATABASE_URL` (transaction pooler) and `DATABASE_CA_CERT` (the
  PEM pasted in). Nothing else — there is no Ollama in production.

### The free tier pauses

Supabase's free tier suspends a project after a stretch of inactivity, which is the wrong
failure mode for a portfolio link: a demo nobody visits turns itself off, and then the one
person who clicks it sees an error. The honest options are to wake it before sharing the link,
to host on something that does not pause, or to skip the hosted demo and rely on the
reproduction steps above, which need no account anywhere.

## Stack

Next.js (App Router) · TypeScript · PostgreSQL + Drizzle · Vitest · Ollama.
Runtime dependencies: `pdf-lib`, `pdfjs-dist`, `sharp`, `zod`, `pg`, `drizzle-orm`.
Document bytes live in Postgres, so a deployment is the app plus a database — no object storage.

The model provider is an interface with exactly two methods, `classify` and `extract`.
Nothing above it knows which model answered — which is what makes the eval portable across
backends, and turns "here are my numbers on a 7B local model" into a comparison rather than
an excuse.

The Ollama adapter calls the HTTP API through native `fetch`: no SDK, no dependency.
